# Quality and Evaluation Report — Team 6: Data Buddies

## 1. Quality checks performed

The team performed automated validation, independent human review, split-integrity checks, and duplicate-text checks on the Luganda Intent Corpus.

### Automated validation

The following command was executed:

```bash
python validate.py --track intent --data data/contribution.csv
```

**Result:** `PASS: 250 records`

The validator confirmed that the dataset passed the required structural checks. However, it does not assess Luganda fluency, semantic correctness, or permission. These remain human-review responsibilities.

### Manual review

- All 250 records were independently reviewed by `REV-LG-2026` for naturalness and intent-label fit.
- All 50 test records were independently reviewed before final evaluation.
- The reviewer is an external fluent Luganda speaker and did not author the records reviewed.
- Reviewer codes are pseudonymous.
- Per-record review decisions are documented in `evidence/REVIEW_LOG.csv`.

### Split integrity

The dataset contains 250 records distributed as follows:

| Split | Records | Records per intent |
|---|---:|---:|
| Training | 150 | 15 |
| Development | 50 | 5 |
| Test | 50 | 5 |
| **Total** | **250** | **25** |

The dataset uses a stratified split, with every intent represented equally in each split. The 50 test records were held back from model training and tuning. Model selection was based on the development set.

### Duplicate-text check

The duplicate-text check identified **zero duplicated `text` values** in the contribution dataset.

## 2. Review, disagreements and exclusions

The independent reviewer assessed each record for:

- Naturalness and clarity of the Luganda utterance.
- Correctness of the assigned intent label.
- Agreement between the intended meaning and the actual utterance.
- Compliance with the annotation guide's label boundaries.

Per-record review decisions and supporting evidence are maintained in `evidence/REVIEW_LOG.csv`.

No individual disagreements or exclusions are detailed in this report. The review log remains the authoritative record for any recorded decisions, disagreements, or excluded examples.

### Data-cleaning decisions

- **Duplicate record IDs:** Fifty duplicate `record_id` occurrences were identified during validation. They were resolved using `fix_ids.py` by adding the `_2` suffix to the second occurrence. The original text and labels were preserved.
- **Text preservation:** Original Luganda spellings, apostrophes, and diacritics were retained. No spelling normalisation was performed.
- **Provenance preservation:** The original `evidence/REVIEW_LOG.csv` was retained as review evidence.

Further details of the ID correction process are documented in `DATA_PLAN.md` and `SOURCE_LOG.md`.

## 3. Model evaluation

The frozen model was evaluated using the 50-record test set. The authoritative evaluation results are stored in the following files:

- `artifacts/intent/test_metrics.json` — overall test metrics, including accuracy and Macro-F1.
- `artifacts/intent/per_label_report.csv` — per-label precision, recall, F1-score, and support, as generated by the evaluation process.
- `artifacts/intent/test_predictions.csv` — individual test predictions, including expected and predicted labels.

Each intent has five test examples, giving a support of five per label.

The reported metrics should be interpreted alongside the small test-set size. In particular, per-label F1-scores are based on only five examples and may change substantially with a different test sample.

### Majority-class baseline

The majority-class baseline provides a simple reference point for evaluating the trained model. Since the dataset is balanced, each of the ten labels has equal representation. The baseline should therefore be calculated from the actual test labels rather than assuming that one intent is the majority class.

## 4. Error analysis

Individual prediction errors should be taken directly from `artifacts/intent/test_predictions.csv`. No predicted errors are reproduced here without consulting the actual evaluation output.

The error analysis should consider the following possible causes where supported by the actual misclassified examples:

- **Character n-gram overlap:** Different intents may contain similar character patterns, causing the model to confuse them.
- **Short inputs:** Brief utterances may provide insufficient character-level information to distinguish between intents.
- **Unseen vocabulary:** Words or word forms not adequately represented in the training data may be misclassified.
- **Similar intent boundaries:** Some requests may have overlapping wording even though their intended actions differ.
- **Luganda morphology:** Variations in word forms and sentence construction may not be adequately captured by a character-based baseline.

These are possible explanations, not confirmed causes for any particular prediction. Actual errors and their likely causes should be interpreted from the test predictions.

## 5. Limitations

### Small test set

The test set contains only five examples per intent. Each per-label F1-score is therefore based on a very small sample and is statistically unstable. Results should be interpreted cautiously and should not be used to make strong comparisons across teams or languages.

### Surface-level model

The baseline uses character-level TF-IDF features with Logistic Regression. Although character features can capture some spelling and word-form patterns, the model does not genuinely understand Luganda morphology, sentence meaning, or context. Unseen vocabulary and variations in phrasing may therefore result in misclassification.

### Uncalibrated probabilities

The confidence scores displayed by the application are not calibrated. They represent the model's output scores and should not be interpreted as reliable probabilities that a prediction is correct.

### No abstention mechanism

The application always predicts one of the ten supported intent labels, even when the submitted input is unclear or outside the dataset's intended scope. It does not currently have a mechanism for rejecting unsupported requests or indicating that no available label is suitable. This limitation is demonstrated in the application demo.

### Dataset scope and language variety

The contribution consists of one team-authored Luganda dataset. It does not represent all Luganda speakers, regional varieties, writing styles, or request domains. The project therefore makes no claim of generalisation across Luganda varieties or unrelated domains.

## 6. Validator limitations

The automated validator confirms structural properties such as required columns, split sizes, and record ID uniqueness.

It cannot independently establish:

- Whether an utterance is natural or fluent Luganda.
- Whether the assigned intent label accurately represents the utterance.
- Whether the source and permission information is genuine and sufficient.
- Whether two different utterances are semantically equivalent.

These aspects require human verification. The team used the author and independent reviewer checks, with provenance and permission information documented in `SOURCE_LOG.md` and review decisions recorded in `evidence/REVIEW_LOG.csv`.
